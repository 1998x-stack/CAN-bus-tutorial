CAN 总线 · 第 11 章 / 接收路径

为什么 CAN 收到了报文，应用却仍然会丢数据？

过滤器、硬件 FIFO、RX 中断、软件缓冲和时效性判断是一条连续的链。任何一段变慢，都可能把“总线收到”变成“业务没处理到”。

01 · 从线缆追踪一条报文

先过过滤器，再进 FIFO，最后才到应用

接收不是一次 memcpy：控制器先验证并过滤帧，把匹配的完整报文存入指定 FIFO；CPU 通过轮询或中断搬运；应用还要确认数据是否及时。

关键区别：FIFO 是硬件暂存区；软件环形队列是 CPU 复制后的第二层缓冲。两个地方都可能溢出，应分别统计。

02 · 容量与覆盖策略

FIFO 已经满了，第 4 帧去了哪里？

bxCAN 以 FMP0/FMP1 表示当前未读帧数（0–3）；FIFO 满时再来匹配报文，会置位 FOVR 溢出标志。RFLM 控制丢失哪一帧，不是“所有芯片都覆盖最老一帧”。

CAN_RFLMFIFO 满时新帧到达工程取舍
DISABLE（未锁定）覆盖 FIFO 内最后存入的那帧尽量保留最新状态，牺牲部分历史
ENABLE（锁定）丢弃本次新帧，保留原有三帧保留较早事件，可能丢失最新状态

不要仅靠增加软件缓存来掩盖硬件 FOVR：如果 ISR 迟迟不运行，数据在进入软件之前就已经丢失。

为什么“有 FIFO，所以中断变少”这个说法不准确？

FMPIE0 使能后，FIFO 内有待处理报文就满足接收挂起条件；不读取、不释放不会消除这件事。FIFO 允许以一次 ISR 批量读出多帧，从而减少频繁进出中断的开销，但需要软件主动采用批处理策略。

03 · 把二进制匹配变成可检查的配置

只接收标准数据帧 0x100–0x10F

11 位标准 ID 的匹配公式可以写成 (received_id & 0x7F0) == 0x100。在 bxCAN 32 位过滤器里，标准 ID 要放到寄存器高半字的 bit15..5；IDE、RTR 也应纳入掩码，否则匹配范围可能包含不想要的帧类型。

// 以已初始化的 CAN1 为前提；示例采用 bxCAN 32-bit mask filter
CAN_FilterInitTypeDef filter = {0};
filter.CAN_FilterNumber = 0;
filter.CAN_FilterMode = CAN_FilterMode_IdMask;
filter.CAN_FilterScale = CAN_FilterScale_32bit;
filter.CAN_FilterIdHigh = (uint16_t)(0x100u << 5);
filter.CAN_FilterIdLow = 0u;               // IDE=0 / RTR=0
filter.CAN_FilterMaskIdHigh = (uint16_t)(0x7F0u << 5);
filter.CAN_FilterMaskIdLow = 0x0006u;      // 必须为标准帧且是数据帧
filter.CAN_FilterFIFOAssignment = CAN_FIFO0;
filter.CAN_FilterActivation = ENABLE;
CAN_FilterInit(&filter);

这里选的是 STM32F1 的寄存器排列方式，不可把这些位移常数原样搬到 FDCAN 或其他控制器。改好过滤器后可依次测试 0x100、0x10F、0x110、扩展帧与远程帧。

04 · 关键代码与时效性

ISR 负责搬运，不负责业务解码

下例采用 STM32F103 常用的 USB_LP_CAN1_RX0_IRQHandler（具体向量以芯片启动文件为准）。代码演示单生产者 ISR / 单消费者主循环的固定长度队列；读写索引由各自一侧更新，使用 CMSIS 屏障发布数据。假设 TickMs() 返回 1 ms 递增的无符号时间。

#include "stm32f10x_can.h"
#include <stdint.h>

#define Q_CAP 16u // 2 的幂；保留一个空槽
typedef struct { CanRxMsg frame; uint32_t tick_ms; } RxEntry;
static RxEntry q[Q_CAP];
static volatile uint8_t head = 0, tail = 0;
static volatile uint32_t q_dropped = 0, hw_overrun = 0;
extern uint32_t TickMs(void);

static void RxPushFromIrq(const CanRxMsg *f) {
    uint8_t next = (uint8_t)((head + 1u) & (Q_CAP - 1u));
    if (next == tail) { q_dropped++; return; }
    q[head].frame = *f;
    q[head].tick_ms = TickMs();
    __DMB();             // 数据就绪后发布 head
    head = next;
}

void USB_LP_CAN1_RX0_IRQHandler(void) {
    if (CAN_GetFlagStatus(CAN1, CAN_FLAG_FOV0) == SET) {
        hw_overrun++;
        CAN_ClearFlag(CAN1, CAN_FLAG_FOV0);
    }
    while (CAN_MessagePending(CAN1, CAN_FIFO0) != 0u) {
        CanRxMsg f;
        CAN_Receive(CAN1, CAN_FIFO0, &f);
        // SPL CAN_Receive() 内部释放 FIFO 输出邮箱（RFOM0）
        RxPushFromIrq(&f);
    }
    // 不需要对 FMP0 做额外“清中断”：读空 FIFO 后挂起条件消失
}

static int RxPop(RxEntry *out) {
    uint8_t pos = tail;
    if (pos == head) return 0;
    __DMB();
    *out = q[pos];
    __DMB();
    tail = (uint8_t)((pos + 1u) & (Q_CAP - 1u));
    return 1;
}

初始化要求：启用 CAN_IT_FMP0 中断与 NVIC 的 USB_LP_CAN1_RX0_IRQn；若要把 FOVR 当独立中断源，还需启用 CAN_IT_FOV0 并在 ISR 做对应处理。共享 USB/CAN 向量需要检查实际 USB 使用方式。示例队列面向单核、单生产者/单消费者，不是可无条件复用的多核通用队列。

读出之后还要问“现在有多旧”

// 主循环：应用定义的最大可接受延迟 25 ms，仅为示例值
void ProcessCanQueue(void) {
    RxEntry item;
    while (RxPop(&item)) {
        const uint32_t age_ms = (uint32_t)(TickMs() - item.tick_ms);
        if (age_ms > 25u) {
            // 记录应用层超时；可按消息 ID 采用不同阈值
            continue;
        }
        // DecodeAndHandle(&item.frame); // 由应用实现
    }
}

无符号减法可在常规计时器回绕下正确计算较短经过时间。超时阈值应由信号周期、抖动、控制时限与安全要求决定，不是统一使用“周期的 1.5 倍”。

05 · 可复现的小实验

用四组输入验证过滤与溢出

实验预期要记录的量
发 0x100 和 0x10F 标准数据帧匹配进入 FIFO0FMP0、软件入队数
发 0x110 标准数据帧被过滤掉FIFO0 无新增
发相同 ID 的远程帧RTR 掩码拒绝FIFO0 无新增
暂时阻断消费并连续注入四帧硬件 FIFO 满时可能 FOVRFOVR0、q_dropped、RFLM 模式

诊断原则：硬件 FOVR、软件队列满、应用过期是三种不同的丢失原因。分别计数，才能找到真正的瓶颈。实验请在隔离测试网络上进行，不要直接在实际车辆的控制网络注入流量。

依据：ST RM0008，bxCAN Reception Handling / Identifier Filtering / CAN_RF0R；STM32F10x SPL CAN_Receive 与 CAN_FilterInit 接口。下一章聚焦 NVIC、中断向量和时间预算。

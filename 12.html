CAN 总线 · 第 12 章 / 中断与实时性

中断越快，CAN 通信就越可靠吗？

答案不是简单地“把优先级调到最高”。真正决定可靠性的，是正确的启动文件向量、短且有界的 ISR、明确的标志处理，以及主循环能够持续消化报文。

01 · 从延迟的来源开始

中断只是数据路径中的一小段

CAN 控制器收到完整有效帧时，若匹配过滤器就将报文写入 FIFO，并在相应使能条件下向 NVIC 提出中断请求。之后才是 CPU 响应、读取、搬运和应用解析。只测 ISR 的执行时间，不能等同于端到端的业务延迟。

要优化的是截止期限，不是某个孤立函数的耗时。 如果应用线程积压，ISR 再快也无法保证信号新鲜。

02 · 找对向量，再谈优先级

STM32F103 的 CAN1 接收 0 中断为什么带 USB 前缀？

STM32F103 的常见启动文件把部分 CAN1 和 USB 中断共享在同一向量上。不能只凭名称缩写写出 CAN1_RX0_IRQHandler，而应以实际 MCU 型号对应的 CMSIS 头文件与启动文件为准。

事件F103 常用 IRQn对应处理函数名
CAN1 发送USB_HP_CAN1_TX_IRQnUSB_HP_CAN1_TX_IRQHandler
CAN1 FIFO0 接收USB_LP_CAN1_RX0_IRQnUSB_LP_CAN1_RX0_IRQHandler
CAN1 FIFO1 接收CAN1_RX1_IRQnCAN1_RX1_IRQHandler
CAN1 状态变化与错误CAN1_SCE_IRQnCAN1_SCE_IRQHandler

这是对常见 STM32F103 设备启动文件的说明；不同 F1 子系列、封装与库版本请按具体向量表核实。使用 USB 与 CAN 共享向量时，还需要设计两者的事件分发。

一段可以对应启动文件检查的配置

#include "stm32f10x_can.h"
#include "misc.h"

void ConfigureCanRx0Irq(void)
{
    NVIC_InitTypeDef nvic = {0};

    // 全系统通常在统一的 NVIC 配置阶段调用一次；不要由各模块争抢
    NVIC_PriorityGroupConfig(NVIC_PriorityGroup_2);

    nvic.NVIC_IRQChannel = USB_LP_CAN1_RX0_IRQn;
    nvic.NVIC_IRQChannelPreemptionPriority = 2;
    nvic.NVIC_IRQChannelSubPriority = 0;
    nvic.NVIC_IRQChannelCmd = ENABLE;
    NVIC_Init(&nvic);

    // 报文已进入 FIFO0 时申请中断；不是“总线出现起始位时”
    CAN_ITConfig(CAN1, CAN_IT_FMP0, ENABLE);
}

数值越小，NVIC 优先级越高。 抢占优先级不同才有抢占关系；子优先级在相同抢占组下决定待处理异常的响应顺序。优先级分组是系统级选择，要同时考虑 RTOS 与其他外设，不要每个驱动自己重新设置。

同抢占优先级的两个中断会互相打断吗？

不会因子优先级不同而相互抢占。它们可能按子优先级先后被服务；若要让一个 ISR 能抢占另一个，需要不同的抢占优先级，而且要考虑最坏执行时间及系统中的其他实时任务。

03 · 事件和清除方式一一对应

别用“进了 ISR 就清所有标志”的思路

bxCAN 的发送、接收和错误事件不应统一当作一个“清标志位”动作。接收 FIFO0 的 FMP0 反映待处理帧数；逐帧调用 CAN_Receive() 会释放输出邮箱，处理完后 FMP0 回落。发送请求完成位 RQCPx 是 W1C，且要先读取 TXOKx 等结果；状态/错误事件有各自的专用状态与清除路径。

来源应当观察正确方向
RX FIFO0FMP0、FULL0、FOVR0读并释放 FIFO；溢出单独计数与清标志
TXRQCPx、TXOKx、ALSTx、TERRx先记录结果，随后 W1C 清对应 RQCPx
SCE / 错误ESR 的 BOFF、EPVF、EWGF、LEC 等区分错误状态与事件来源，按参考手册处理

下例把 CAN1 RX0 ISR 的动作压缩为“批量取帧 + 交给已有的单生产者队列”，它依赖第 11 章已经实现的 RxPushFromIrq()。集成时请将第 11 章中的静态辅助函数与本 ISR 放在同一源文件，或改成合适的模块接口；避免重复定义 IRQHandler。

// 与第 11 章的 RxPushFromIrq() 放在同一编译单元
volatile uint32_t can_rx_irq_count = 0;

void USB_LP_CAN1_RX0_IRQHandler(void)
{
    can_rx_irq_count++;

    while (CAN_MessagePending(CAN1, CAN_FIFO0) != 0u) {
        CanRxMsg frame;
        CAN_Receive(CAN1, CAN_FIFO0, &frame);
        RxPushFromIrq(&frame);
    }

    // RX FIFO0 挂起随 FIFO 读空而撤销；不要随意清其他事件
}

ISR 的边界：避免 printf、动态内存、长延时和不受控循环。上述“读到 FIFO 空”的方式适合一般负载，但如果新报文持续高速涌入，也应测试最坏 ISR 占用时间，必要时采用有界批处理与再次触发策略。

04 · 从感觉走向测量

怎样知道中断到底占用了多少时间？

可以在 ISR 入口置位 GPIO、出口复位 GPIO，再用逻辑分析仪读取脉宽；这测得的是包含探针开销的 ISR 执行时间，不是“报文上总线到进入 ISR”的完整响应延迟。另可在 Cortex-M3 上使用 DWT CYCCNT 统计周期数（需开启计数器，且不同芯片和调试状态要验证支持）。

// 在系统初始化阶段打开周期计数器（Cortex-M3）
CoreDebug->DEMCR |= CoreDebug_DEMCR_TRCENA_Msk;
DWT->CYCCNT = 0u;
DWT->CTRL |= DWT_CTRL_CYCCNTENA_Msk;

// 在 ISR 入口、出口分别采样 DWT->CYCCNT；
// 使用无符号差值统计，勿在 ISR 中打印。
const uint32_t cycles = end_cycles - start_cycles;
// 72 MHz 主频时：720 cycles / 72 MHz = 10 us
// 720 仅用于演示换算，不是实测结果。

使用 DWT 或 GPIO 的数据前，要核对当前系统时钟、优化等级、探针开销以及是否允许抢占。打断点会改变时序，不能拿单步调试结果代表实时运行。

05 · 形成故障定位闭环

遇到“只中断一次”该从哪里查？

现象检查顺序
ISR 完全不进启动向量名 → NVIC IRQn → CAN_ITConfig → FIFO 过滤器 → 物理层与 ACK
ISR 只进一次FIFO 是否已读空 → 是否有残留 FMP / 错误源 → 中断使能状态
高负载丢帧FOVR → 软件队列满 → 中断最长耗时 → 应用任务周期
系统周期抖动抢占分组 → 高优先级 ISR 用时 → 是否在 ISR 里阻塞 / 打日志
Bus-off 后不恢复ESR 错误计数与 BOFF → 物理故障 → ABOM/恢复策略与重发时限

工程边界：volatile 使共享变量的访问保持可观察性，但它不能替代原子操作、内存顺序或临界区。共享队列必须按明确的单生产者/单消费者或带锁协议设计，不应笼统地宣称“加 volatile 就没有竞争”。

课后实验：在隔离 CAN 测试网上设置 10 ms 周期的消息，逐步引入可控的主循环延迟；同时记录 CAN FIFO 溢出、软件队列满次数、ISR 周期分布和业务消息年龄。观察哪个指标先触及应用的时限。

依据：ST RM0008，bxCAN Interrupts / CAN_IER / CAN_TSR / CAN_RF0R；ST 的 STM32F103xB 启动向量表。下一章进一步拆解接收过滤器的工作方式。

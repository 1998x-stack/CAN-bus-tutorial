CHAPTER 18 · CANOPEN CC

CAN 帧只有 ID 和数据，设备怎么知道这是什么意思？

两台设备都能发送 CAN 帧，不代表能理解彼此的温度、速度和配置参数。CANopen 在经典 CAN 的报文之上定义了一个共同“词典”和几类通信方式：先用对象字典命名数据，再分别用 SDO、PDO 和网络管理服务访问它们。

阅读路径：分层模型 → 对象字典 → PDO 映射 → SDO 字节拆解 → 上线顺序

18.1 在 CAN 之上，补齐“数据的语义”

本章讨论基于经典 CAN 的 CANopen CC（CiA 301），不混同于 CANopen FD。底层 CAN 负责仲裁、帧校验与链路 ACK；CANopen 规定对象字典、通信对象、网络状态和设备配置方式。[CiA：CANopen 概览]

在 CiA 301 的预定义连接集里，节点 ID 通常取 1～127，常见 11-bit COB-ID 如下。注意“默认”不等于每台设备实际配置永远固定：PDO 与部分通信对象的 COB-ID 可通过对象字典参数配置。[CiA：设备内部结构]

对象常见 COB-ID用途
NMT 命令0x000改变节点通信状态，数据域含命令与目标节点
SYNC0x080同步触发基准（在采用此默认配置时）
TPDO1 / RPDO10x180+n / 0x200+n默认过程数据通道
SDO 服务器发送 / 接收0x580+n / 0x600+n服务端应答 / 接收客户端请求
心跳/Boot-up0x700+n反映节点启动和 NMT 状态

18.2 对象字典：索引不是随意取的表格编号

一个对象通过 16-bit Index + 8-bit Sub-index 定位，条目还包含数据类型、访问权限和当前值。0x1000:00 是 Device type，0x1001:00 才是 Error register；0x0000 不是设备类型。多数记录/数组以子索引 0 说明条目数量，而变量对象通常只使用子索引 0。不能把某个对象的子索引 1 凭空解释成另一个对象。[CANopenNode：对象字典]

范围 / 例子职责读取时注意
0x1000–0x1FFF通信参数0x1000:00 设备类型；0x1017:00 生产者心跳周期
0x1018Identity record子索引 1～4 对应厂商、产品、修订和序列号（设备支持时）
0x2000–0x5FFF制造商特定对象含义以 EDS/XDD 或厂家文档为准
0x6000–0x9FFF标准化设备协议对象需结合 CiA 401、402 等设备协议
拿到一台新设备时，先取得与固件版本对应的 EDS/设备手册，再核对 0x1000、0x1018、0x1017、0x1200 和 PDO 通信/映射参数。是否可写、是否支持动态映射，由设备实现决定。

18.3 PDO：事先谈好布局，之后只发送数据

TPDO 是某设备产生的过程数据，RPDO 是某设备消费的过程数据。PDO 帧内通常不附带对象索引，这是它通信开销低的原因；但它并非“没有协议开销”，CAN 帧本身仍有仲裁、控制、CRC、ACK 等字段。PDO 通常没有 SDO 式应用层请求/应答，发送成功也不能推出业务应用已经消费数据。[CiA：PDO 协议]

映射项由 32 位描述符给出：高 16 位为对象索引，中间 8 位为子索引，低 8 位为位长。下面是假设设备允许映射、仅用于教学的 48-bit TPDO 示例：

通信参数在 0x1800…（TPDO）与 0x1400…（RPDO），映射记录在 0x1A00… 与 0x1600…。映射修改通常需要先禁用相关 PDO、按设备要求设置映射数量与条目、再启用，不能在运行中不加检查地直接修改。

不要把 PDO 的“异步”写成“值改变必然触发”。是否周期、事件或 SYNC 驱动，取决于 Transmission type、事件定时器、抑制时间与设备能力。CANopen CC 的 PDO 通常在 NMT Operational 状态下进行；Pre-operational 允许配置用的 SDO，但不进行 PDO 通信。[CiA：NMT]

18.4 SDO：按地址询问设备，再核对它的回答

SDO 是客户端—服务器协议。对一个默认 SDO 服务器，客户端请求使用 0x600 + Node-ID，服务器应答使用 0x580 + Node-ID。下面读取 0x1017:00（生产者心跳时间，UNSIGNED16）。请求的 index 采用低字节在前，因此 0x1017 在帧里是 17 10。[CiA：SDO 协议]

字节位置读取请求示意应答解释
0404B请求上传 / 两字节有效数据的 expedited upload 响应
1–217 1017 10Index = 0x1017（小端序）
30000Sub-index = 0
4–700 00 00 0064 00 00 00仅应答前两字节有效 → 100 ms

并非所有 SDO 应答都按“字节 4–7 直接解释为四字节数值”：还存在分段和块传输、不同长度的快速传输、以及以 0x80 开头的 abort 响应。客户端必须检查命令字、索引、子索引、长度、超时与 abort code；一问一答并不意味着掉帧后协议会自动确保最终写入成功，重试及失败策略需由具体栈和应用实现。

交互小实验｜改变 Node-ID，观察默认 SDO 通道

只更改节点号，数据域请求依旧在读 0x1017:00。这是预定义连接集示例；实际设备可能重配置 SDO COB-ID。

请求 COB-ID 0x601：40 17 10 00 00 00 00 00；应答 COB-ID 0x581。 
# Python 3 · 预定义连接集 SDO 请求编码（不访问真实设备）
def sdo_read_1017(node_id):
    if not (1 <= node_id <= 127):
        raise ValueError("Node-ID outside 1..127")
    return 0x600 + node_id, bytes.fromhex("40 17 10 00 00 00 00 00")

assert sdo_read_1017(1) == (0x601, b"\x40\x17\x10\x00\x00\x00\x00\x00")
# 示例应答：0x4B 的有效载荷长度为 2 字节
response = bytes.fromhex("4B 17 10 00 64 00 00 00")
assert int.from_bytes(response[4:6], "little") == 100
assert (0x6041 << 16) | (0 << 8) | 16 == 0x60410010
assert (0x606C << 16) | (0 << 8) | 32 == 0x606C0020

18.5 第一台 CANopen 设备怎样安全上线？

  1. 先检查总线物理层、双方位速率和 Node-ID 唯一性，获取固件匹配的 EDS/设备手册。
  2. 监听 Boot-up（默认 0x700+n，数据 00）和后续心跳，区分通信可达与应用已进入 Operational。
  3. 在 Pre-operational 状态使用 SDO 读 0x1000:00、0x1018 等，核对访问类型和读写返回。
  4. 按设备说明配置 PDO 映射、通信参数及心跳监控，再通过 NMT 切到 Operational。
  5. 接收并解码 PDO，联动监控 EMCY、心跳超时与错误计数；关键命令需要应用层闭环验证。
下一章 NMT 与心跳 会解释通信状态机与节点存活检测；后续 SDO 通信 与 PDO 通信 进一步展开各自的帧与配置。不要把“总线上有报文”与“应用业务已生效”画等号。

CAN 总线 · 第 10 章 / 发送路径

一条 CAN 报文，何时才算真正发出去？

从软件提交、三个 bxCAN 发送邮箱，到线上逐位仲裁与完成状态：区分“接受发送请求”和“总线上成功发送”，才能写出可诊断的发送程序。

先厘清误解本地调度代码与状态故障定位

01 · 先厘清一个误解

调用 CAN_Transmit() 不等于发送成功

假设 10 ms 内必须发出 ID 为 0x100 的控制帧。函数返回了邮箱号，难道接收节点就已经收到了吗？并没有。返回邮箱号只表示控制器接受了请求，后面可能还要等空闲总线、竞争仲裁、检测错误与获得 ACK。

三件不同的事：软件申请到了邮箱；控制器完成了一次发送请求；CAN 控制器确认成功发送（TXOK）。应用层收到并处理是更高层的协议问题，不能从 TXOK 推断。

02 · 拆开本地调度

为什么邮箱编号不决定 CAN 优先级

STM32F1 bxCAN 有三个发送邮箱，忙碌期间其报文寄存器由硬件保护。多个邮箱同时待发时，CAN_TXFP = DISABLE 让本地选择偏向报文标识符优先级；CAN_TXFP = ENABLE 则按请求先后顺序。真正的总线仲裁仍由发送中的 CAN 帧标识符及相关位决定。

位置IDTXFP=DISABLETXFP=ENABLE
邮箱 00x300后于 0x100 / 0x200由请求时间决定
邮箱 10x100本地优先由请求时间决定
邮箱 20x200次于 0x100由请求时间决定
想一想：把紧急报文强行放进邮箱 0，就一定先发吗？

不一定。SPL 的 CAN_Transmit() 会选择可用邮箱；三个邮箱全部占用时，新报文进不去。即使找到邮箱，也要面对本地调度和外部节点仲裁。要保障时限，需要软件队列的优先级、明确的过期策略和总线负载预算。

03 · 把代码与状态对应起来

最小安全发送：校验、提交、确认

以下为 STM32F10x Standard Peripheral Library（经典 CAN，非 CAN FD） 示例。前置条件：CAN1/GPIO/波特率已初始化，总线有另一正常节点参与 ACK，且调用方不会并发改写同一软件队列。

#include "stm32f10x_can.h"
#include <stdint.h>
#include <stddef.h>

uint8_t CAN_SendStandard(uint16_t id, const uint8_t *bytes, uint8_t dlc)
{
    if (id > 0x7FFu || dlc > 8u || (dlc != 0u && bytes == NULL))
        return CAN_TxStatus_NoMailBox;

    CanTxMsg msg = {0};
    msg.StdId = id;
    msg.IDE   = CAN_Id_Standard;
    msg.RTR   = CAN_RTR_Data;
    msg.DLC   = dlc;
    for (uint8_t i = 0; i < dlc; i++)
        msg.Data[i] = bytes[i];

    // 0、1、2：请求进入的邮箱；NoMailBox：当前没有空位
    return CAN_Transmit(CAN1, &msg);
}

// 用法：记录返回邮箱号，后续通过状态查询或 TX 中断确认结果。
// 切勿把“返回 0..2”直接记为“成功发送”。

CAN_TransmitStatus(CAN1, mailbox) 可以用于受控的轮询场景，但要保证邮箱在查询期间不会被复用。更稳妥的异步方案是在 TX 中断中立即读取对应邮箱的 RQCP/TXOK/ALST/TERR，并将结果转交给主循环。

TX 中断应怎样记录结果？

// STM32F103 常用启动文件中的共享向量：USB_HP_CAN1_TX
// 需先 NVIC 使能 USB_HP_CAN1_TX_IRQn，并 CAN_ITConfig(CAN1, CAN_IT_TME, ENABLE)。
volatile uint32_t tx_ok_count = 0, tx_fail_count = 0;

void USB_HP_CAN1_TX_IRQHandler(void)
{
    const uint32_t tsr = CAN1->TSR; // 快照：先看结果，再清除

    if ((tsr & CAN_TSR_RQCP0) != 0u) {
        if (tsr & CAN_TSR_TXOK0) tx_ok_count++;
        else tx_fail_count++; // 另查 ALST0 / TERR0 / 是否中止
        CAN1->TSR = CAN_TSR_RQCP0; // W1C：只清该邮箱完成位
    }
    if ((tsr & CAN_TSR_RQCP1) != 0u) {
        if (tsr & CAN_TSR_TXOK1) tx_ok_count++;
        else tx_fail_count++;
        CAN1->TSR = CAN_TSR_RQCP1;
    }
    if ((tsr & CAN_TSR_RQCP2) != 0u) {
        if (tsr & CAN_TSR_TXOK2) tx_ok_count++;
        else tx_fail_count++;
        CAN1->TSR = CAN_TSR_RQCP2;
    }
    // 若 USB 与 CAN 共用向量，必须协调共享中断源处理。
}

留意 W1C 寄存器：对完成标志使用明确的写 1 清除，而不是对 TSR 做不加区分的按位或读改写。RQCP=1 不等于 TXOK=1；仲裁丢失、传输错误、中止及关闭自动重传配置都影响状态解释。

04 · 让故障可定位

发送卡住时，先问哪一个环节失败？

观测优先排查下一步
返回 NoMailBox三个邮箱忙；软件提交速度大于发送能力限流、队列、deadline 与邮箱占用时长
RQCP 置位但 TXOK 未置位查看 ALST/TERR、NART、是否被中止读 ESR 与总线分析仪日志
长期没有成功完成ACK 缺失、线缆与终端、波特率、总线关闭检查另一节点、ESR、收发器状态
低 ID 帧仍超时本地队列、TXFP、总线负载与仲裁竞争度量“入队→TXOK”延迟分位数

发送一帧至少占用多久？

总线是共享介质：在某个位速率下，一帧的线上时间由它实际占用的位数决定。用下面的估算式可以粗估期限 D 内最多能排几帧；不含位填充、仲裁失败与错误重传，属于教学示意。

tframe=BR

B 默认取第 02 节的教学估算；实机应以总线抓包测得的位填充后长度与延迟分位数为准。

练习：同时排队 ID=0x300 与 ID=0x100，分别测试 TXFP 两种设置；记录请求顺序、实际 TXOK 次序与错误计数。在两节点且物理层正确的网络上验证，不要用单节点无 ACK 的情形误判为发送 API 错误。

依据：ST RM0008，bxCAN Transmission Handling / CAN_TSR；STM32F10x SPL 的 CAN_Transmit / CAN_TransmitStatus 接口。下一章把镜头转向接收 FIFO。

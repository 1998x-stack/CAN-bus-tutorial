第23章 J1939 多包传输：50 字节怎样通过 8 字节 CAN 帧？

从“拆成 8 包”这个简单答案出发，逐步认识 BAM、RTS/CTS、TP.DT，以及真正决定连接完成的是谁。

23.1 为什么不能直接连续发送 8 帧？

Classical CAN 的一帧最多携带 8 字节。假设一个 J1939 参数组有 50 字节：即使发送方连续广播 8 个普通帧，接收方也无法只凭它们的 ID 知道“哪个是第几包、何时结束、原本属于哪个 PGN”。

J1939-21 的传统 Transport Protocol（TP） 用两个专用 PGN 把这件事讲清楚：TP.CM = 60416 (0xEC00) 发控制信息，TP.DT = 60160 (0xEB00) 发连续编号的数据包。每个 TP.DT 帧第 1 字节放序号，因此只剩 7 字节有效数据空间。

N=⌈L7⌉,9≤L≤1785

这里 L 是原始 PGN 的字节数，N 是 TP.DT 包数；上限是 255 包 × 7 字节 = 1785 字节。

50 字节 → 8 包，最后 1 字节有效载荷 + 6 字节填充
本章的上限与帧格式针对 J1939-21 的传统 TP。J1939-22（CAN FD）与 Extended Transport Protocol（ETP）具有不同的机制和限制，不能把 1785 字节上限泛化到所有 J1939 传输。

23.2 两条路径：广播 BAM，还是目的地址明确的 RTS/CTS？

真正的分叉点不在“数据有多大”，而在接收方是否需要控制发送节奏。广播 BAM（Broadcast Announce Message）由发送方公布总长度、包数和原 PGN，然后向全网依次发送 TP.DT；没有 CTS，也没有结束确认。RTS/CTS（Connection Mode Data Transfer, CMDT）则先向指定 DA 请求发送，接收方决定这一轮准许几包，收齐后由接收方返回 EOM ACK。

维度BAMRTS/CTS（CMDT）
目标全网广播（DA = 0xFF）一个特定目标地址
开始BAM（控制码 0x20）RTS（0x10）与 CTS（0x11）握手
数据阶段按协议要求的间隔发送 TP.DT按 CTS 放行的包数发送 TP.DT
结束接收方按长度/包数重组，无最终确认接收方发送 EOM ACK（0x13）
失败处理不能依赖接收端确认可通过 Abort（0xFF）终止会话

23.3 控制帧携带原 PGN，数据帧只携带序号与内容

一个容易忽略的细节：0xEC00 和 0xEB00 只是传输通道，并不是正在传输的业务 PGN。TP.CM 的最后三个字节按低字节在前给出原始 PGN。例如原 PGN 0x00FF00 写作 00 FF 00。

控制帧Byte 1–8（十六进制）发送方
RTS，50 字节 / 8 包 / 每轮至多 8 包10 32 00 08 08 00 FF 00原发送方
CTS，允许包 1–811 08 01 FF FF 00 FF 00接收方
EOM ACK，确认整条消息13 32 00 08 FF 00 FF 00接收方
BAM，宣布 50 字节20 32 00 08 FF 00 FF 00原发送方
TP.DT #101 [7 字节业务数据]原发送方
TP.DT #808 [最后 1 字节] FF FF FF FF FF FF原发送方

按地址构造的例子：发送方 SA 0x80、接收方 DA 0x90，优先级 6 时，RTS 的 CAN ID 是 0x18EC9080，CTS 与 EOM ACK 的 CAN ID 是 0x18EC8090，数据帧 ID 为 0x18EB9080。广播 BAM 则使用 0x18ECFF80。

约束：CTS 宣告的本轮包数不能大于接收端可处理的容量，也不能超出发送方 RTS 所宣告的每轮最大包数。CTS 可以分多轮发送；不能把第一轮收到 8 包当成所有消息都能一次完成。

23.4 超时是状态机的一部分，不存在统一“自动重传三次”

传统 TP 会话的等待时间按状态分配；一个常见的 SAE J1939-21 时间参数组合如下。工程实现必须按采用的标准版本和协议栈状态进行处理，不应把所有超时机械地设为 750 ms。

定时器典型值等待哪件事
T1750 ms接收端等待连续 TP.DT 数据包
T21250 ms接收端发出 CTS 后等待首个 TP.DT
T31250 ms发送端等待 CTS、下一轮 CTS 或 EOM ACK
T41050 ms发送端收到 CTS(0) 暂停指示后等待后续处理

超时后应按会话状态终止、报告错误并清理缓存；协议并没有“任何情况下超时就自动重发整条消息三次”的通用规则。BAM 更没有接收者反馈通道。要求端到端确认或重试，应由上层业务协议另行设计。

23.5 用 20 行 Python 验证分包与重组

这段代码只演示 TP.DT 有效负载的序号与填充规则，不是完整 J1939 协议栈。真实产品还要处理地址、PGN、BAM/RTS/CTS 状态、定时器、会话交错及 Abort。

def split_tp(data: bytes) -> list[bytes]:
    assert 9 <= len(data) <= 1785
    packets = []
    for i in range(0, len(data), 7):
        seq = i // 7 + 1
        chunk = data[i:i+7]
        packets.append(bytes([seq]) + chunk.ljust(7, b"\xff"))
    return packets

def join_tp(packets: list[bytes], total_size: int) -> bytes:
    expected = (total_size + 6) // 7
    assert 9 <= total_size <= 1785
    assert len(packets) == expected
    for n, packet in enumerate(packets, 1):
        assert len(packet) == 8 and packet[0] == n
    data = b"".join(packet[1:] for packet in packets)
    assert data[total_size:] == b"\xff" * (len(data) - total_size)
    return data[:total_size]

payload = bytes(range(50))
packets = split_tp(payload)
assert len(packets) == 8
assert packets[-1] == bytes([8, 49, 255, 255, 255, 255, 255, 255])
assert join_tp(packets, 50) == payload

如果故意交换第 2 包和第 3 包，join_tp 会失败。这比“把收到的数据直接拼接起来”多出的正是序号检查；生产代码还要校验每个会话的源/目标和原 PGN。

23.6 参考规范与下一步

具体控制码、长度与状态机以 SAE J1939-21 及适用的栈文档为准。可公开核对的实现依据包括 Linux J1939 传输层说明、Linux TP 状态机源码 和 J1939-21 定时器说明。这些资料不替代标准原文。
